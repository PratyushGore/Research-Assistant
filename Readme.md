### Plain-English Model Reference Guide

1. **`OutputType` (Enum)**: Represents the target deliverable types supported by the pipeline (`Literature Survey`, `Executive Summary`, `PPT`, `Research Paper`). It is selected by the user via the **Guided Input Agent** and consumed across the pipeline, specifically by the **Composer Agent** and **Document Review Agent** to determine structuring, depth, and layout criteria.

2. **`CoverInfo`**: Captures metadata for the document title or presentation cover page, such as title, subtitle, author list, institution, and date. It is collected and emitted by the **Guided Input Agent** and consumed by the **Composer Agent** to generate the title page or opening slide.

3. **`ProjectPresentationInfo`**: Encapsulates presentation-specific parameters such as slide count, audience type, tone, and focus highlights. It is generated by the **Guided Input Agent** whenever `PPT` is one of the requested outputs and consumed directly by the **Composer Agent** to outline and format slide decks.

4. **`AcademicContentInfo`**: Defines scholarly configuration options such as citation formatting preferences, target journal/venue standards, methodology preferences, and field-specific keywords. It is produced by the **Guided Input Agent** and consumed by the **Citation Agent**, **Composer Agent**, and **Document Review Agent**.

5. **`OutputTemplate`**: Defines the structural blueprint (e.g., specific section headings and narrative guidelines) corresponding to each output format. It is loaded/provided as configuration alongside the **Guided Input Agent** or orchestrator and consumed by the **Composer Agent** to structure drafted content according to preset sections.

6. **`GuidedInputBundle`**: Serves as the consolidated intake contract that bundles the research topic, requested output formats, cover details, presentation specs, academic specs, and user notes into a single package. It is produced by the **Guided Input Agent** and consumed as the master input for the **Search Agent**, **Composer Agent**, and pipeline orchestrator.

7. **`PaperMetadata`**: Holds bibliographic information about a scientific publication, including paper ID, title, authors, year, abstract, venue, DOI, and URL. It is generated by the **Search Agent** (and supplemented by the **Ingestion Agent**) and consumed by the **Summarization Agent**, **Citation Agent**, and **Composer Agent**.

8. **`SearchResult`**: Wraps the result of a research query, containing the search query string, matching paper metadata records, and hit counts. It is produced by the **Search Agent** and consumed by the **Ingestion Agent** to determine which candidate papers to fetch and parse.

9. **`Chunk`**: Represents a discrete, segmented text excerpt from a paper, labeled with chunk ID, parent paper ID, optional section heading, and page number. It is generated by the **Ingestion Agent** and consumed by the **Summarization Agent** for extraction and the **Verification Agent** as ground-truth evidence.

10. **`IngestionResult`**: Packages the complete parsing output of a single paper, containing its metadata, list of extracted text chunks, and raw extracted text. It is produced by the **Ingestion Agent** and consumed by the **Summarization Agent**.

11. **`Claim`**: Represents an isolated empirical or factual statement extracted from a paper, linked back to its source paper ID and chunk IDs, with an execution state (`verification_status`) and revision counter. It is instantiated by the **Summarization Agent**, evaluated and updated by the **Verification Agent**, and consumed by the **Composer Agent**.

12. **`PaperSummary`**: Encapsulates the synthesized overview of an individual research paper, its key takeaways, and all claims extracted from it. It is created by the **Summarization Agent** and consumed as an element of the aggregated findings packet.

13. **`FindingsPacket`**: Collects the collective intelligence of the literature review stage across all processed papers, including per-paper summaries and all extracted claims. It is assembled and emitted by the **Summarization Agent** and consumed by the **Verification Agent**, **Composer Agent**, and **Document Review Agent**.

14. **`VerificationResult`**: Carries the fact-checking judgment for an individual claim against its source chunks, including status (e.g., verified, refuted), confidence score, supporting chunk IDs, and natural language explanation. It is produced by the **Verification Agent** and consumed by the **Composer Agent** (to filter out unverified claims) and the **Document Review Agent**.

15. **`FormattedCitation`**: Contains a single paper's citation formatted to the requested reference style, providing both the in-text marker (e.g., `[1]` or `(Author, 2023)`) and the complete bibliographic text. It is generated by the **Citation Agent** and consumed by the **Composer Agent** for in-text placement and bibliography construction.

16. **`CitationResult`**: Gathers all formatted in-text citations and the finalized, sorted reference bibliography for the research run. It is produced by the **Citation Agent** and consumed by both the **Composer Agent** and **Document Review Agent**.

17. **`ComposerRequest`**: Gathers all verified claims, synthesized findings, citation entries, template guidelines, and guided inputs required to compose a specific deliverable. It is created by the pipeline orchestrator and consumed as the primary input by the **Composer Agent**.

18. **`ComposerResult`**: Contains the finished drafted deliverable for a specific output type, detailing title, complete Markdown/text content, structured sections, and citations used. It is produced by the **Composer Agent** and consumed by the **Document Review Agent** and the presentation layer.

19. **`DocumentReviewRequest`**: Packages a drafted deliverable together with the underlying source findings, verification logs, and citation records for internal auditing. It is assembled by the pipeline orchestrator and consumed by the **Document Review Agent**.

20. **`DocumentReviewResult`**: Delivers the document review audit outcome, including a pass/fail flag, overall evaluation score, detailed review feedback, identified issues, and suggested revisions. It is produced by the **Document Review Agent** and consumed by the orchestrator to decide whether to finalize or trigger a revision loop.

21. **`UserQARequest`**: Intake model for the always-on student Q&A chat feature, capturing `question` and `topic`. Sent by Person C's frontend and consumed by the **User QA Agent** (Person B/D) via the standalone `qa_graph`.

22. **`UserQAResponse`**: Response model for the always-on user chat, returning the synthesized `answer` and grounding `source_paper_ids`. Produced by the **User QA Agent** and consumed by the frontend client.

23. **`PipelineRequest`**: The initial ingress payload initiating a LangGraph pipeline execution run, bearing a request ID and user-configured guided input bundle. It is submitted by the client/API layer and consumed by the LangGraph orchestrator.

24. **`PipelineStatus`**: An in-memory status descriptor tracking pipeline execution progress, active agent stage, status flags (`pending`, `in_progress`, `completed`, `failed`), errors, and completed deliverables. It is maintained and updated by the orchestrator and consumed by polling/streaming API endpoints.

### Open Questions & Clarifications for the Team

1. **`OutputType` String Formatting**: Are downstream agents expecting exact display names (`"Literature Survey"`, `"Executive Summary"`, `"PPT"`, `"Research Paper"`) or lowercase snake_case enum values (`"literature_survey"`, `"executive_summary"`, `"ppt"`, `"research_paper"`) when serializing to JSON?
2. **`VerificationResult` Status Values**: Should we restrict `verification_status` in `VerificationResult` and `Claim` to an explicit `Enum` (e.g., `PENDING`, `VERIFIED`, `REFUTED`, `INSUFFICIENT_EVIDENCE`) rather than an open string?
3. **`DocumentReviewResult` Loop Trigger**: When `passed=False` in `DocumentReviewResult`, should the orchestrator pass `suggested_revisions` back to the **Composer Agent** (via a revision field in `ComposerRequest`), or should it trigger an upstream revision in the **Summarization Agent** / **Verification Agent**?


### How to Plug In Your Agent
Each teammate can plug their agent logic into `backend/orchestrator/graph.py` without altering the graph's structure or wiring.

#### 1. Function Signature to Match
Every agent node in LangGraph is a function that receives the current `PipelineState` dictionary and returns the updated `PipelineState` (or a dictionary of the updated fields).

```python
from backend.orchestrator.graph import PipelineState

def your_agent_name(state: PipelineState) -> PipelineState:
    # 1. Read what you need from state
    # e.g., input_data = state.get("guided_input")
    # 2. Execute your agent logic
    # ...
    # 3. Update state with your schema-compliant result
    # e.g., state["search_results"] = your_search_result
    return state
```

| Agent Stub Function | Current Stub Location | State Field Primarily Read / Updated |
| :--- | :--- | :--- |
| `guided_input_agent` | `backend/orchestrator/graph.py` | Reads `request_id`, sets `guided_input` |

| `citation_agent` | `backend/orchestrator/graph.py` | Reads `findings` and style, sets `citations` |

To integrate an external module, replace the stub body with a delegate call to your module (e.g., `from backend.agents.search import run_search` and call `run_search(state)`).
